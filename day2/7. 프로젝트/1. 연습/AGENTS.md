# AGENTS.md — ML 프로젝트 작업 규칙

이 프로젝트는 세 종류의 공간을 분리해서 관리합니다.

- **탐색 노트북(`*.ipynb`)**: EDA·전처리 확인처럼 **모델 학습이 없는** 시행착오를 자유롭게 하는 공간입니다. 기록 의무가 없고, 마음껏 덮어써도 됩니다.
- **`experiments/*.py`**: (1) 모델을 실제로 학습·평가하는 작업은 전부, (2) 노트북에서 확인한 것 중 "정식으로 남길 만한" EDA/전처리 결과를 재현 가능한 스크립트로 정리한 파일입니다. 실행하면 지표·그래프·제출 파일을 남깁니다.
- **`dashboard_template.py`**: Streamlit 대시보드. `experiments/*.py`의 실행 결과를 모아 비교해서 **보여주는** 파일입니다. 직접 손으로 채우지 않습니다.

## 1. 탐색 노트북에서 자유롭게 작업 (모델 학습 제외)

사용자가 "이 변수 분포 보여줘", "결측치 확인해줘", "이 컬럼이랑 정답이랑 관계 있어?" 처럼 **모델 학습이 없는** 확인·탐색성 요청을 하면:

- 노트북 셀에 코드를 작성하고 바로 실행해서 결과를 보여준다.
- `experiments/`에 파일을 만들거나 `dashboard_template.py`를 건드리지 않는다.
- 노트북은 기록·평가 대상이 아니므로 중간 결과가 실패하거나 지저분해도 괜찮다. 자유롭게 다시 쓰고 덮어써도 된다.
- 단, 모델을 실제로 학습(fit)시키는 요청이 섞여 있으면 그 부분은 노트북이 아니라 아래 2번 규칙을 따른다.

## 2. 정식 실험은 experiments/에 스크립트로

작업을 아래 두 경우로 나눠서 판단한다.

### (가) 모델 학습·평가 — 항상 experiments/로
"랜덤포레스트로 학습해줘", "파라미터 바꿔서 다시 학습해줘", "이 모델 성능 평가해줘"처럼 **모델을 실제로 학습시키거나 평가하는 지시는, 사용자가 따로 "기록해줘"라고 말하지 않아도 항상** `experiments/`에 스크립트로 만든다. 노트북에서 모델을 학습시켜서 결과만 잠깐 보여주고 끝내지 않는다.

### (나) 모델 학습이 없는 EDA/전처리 — 기록 요청이 있을 때만
결측치 분포 확인, 전처리 아이디어 비교처럼 모델 학습이 없는 탐색은 노트북에서 진행하다가, 사용자가 "이걸로 기록해줘", "제출 파일 만들어줘", "이 실험 정리해줘", "대시보드에 반영해줘"처럼 **남기고 싶다는 의사를 밝혔을 때만** `experiments/`로 옮긴다.

### 공통 규칙
- **`dashboard_template.py`를 직접 수정하지 않는다.**
- 노트북에서 이미 확인한 코드가 있으면 그 로직을 재사용해서 정리한다. 처음부터 다시 탐색하지 않는다.
- 파일명 규칙: `experiments/YYYY-MM-DD_짧은설명.py`
  - 예: `experiments/2026-09-09_baseline_rf.py`, `experiments/2026-09-09_impute_median.py`
- 스크립트는 실행 결과(지표, 그래프, 표 등)를 터미널 출력이나 저장 파일(예: PNG, CSV)로 남겨서 사용자가 바로 확인할 수 있게 한다.
- 실행이 끝나면 결과를 간단히 요약해서 사용자에게 보고한다.
- 기존 `experiments/*.py` 파일을 다시 열어서 이어서 실험하는 것은 괜찮다.

## 3. dashboard_template.py 수정 조건

다음 두 가지 경우에만 `dashboard_template.py`를 수정한다.

### (a) 자동 기록 — EDA / 모델 학습·평가 결과
대시보드는 "EDA/전처리 결과"와 "모델 학습 결과" 두 페이지로 구성된다. `experiments/`의 스크립트를 실행해서 다음과 같은 결과가 나오면, **사용자가 별도로 요청하지 않아도 항상 자동으로** 해당 페이지에 반영한다.

- EDA 통계, 결측치/0값 분포, 변수 요약 등 → "EDA/전처리 결과" 페이지
- 모델 학습 후 지표(accuracy, precision, recall, f1, rmse, mae 등)
- 혼동행렬 / 잔차 플롯
- Error Analysis 결과 (오류율 구간별 분석)
- Feature importance / SHAP (XAI)

반영 규칙:
- **첫 실제 기록을 반영할 때**: 지금 대시보드에 들어있는 내용(예시 `runs`인 "1차 시도"/"2차 시도", `feature_A/B/C` 같은 예시 변수명, 예시 혼동행렬·error_breakdown·feature_importance 등)은 모두 레이아웃을 보여주기 위한 placeholder다. 실제 결과가 처음 들어오면 이 예시들을 지우고 그 자리를 실제 결과로 채운다.
- 새로운 실행(run)은 `runs` 리스트에 새 딕셔너리로 **추가**한다 (실제 기록이 쌓이기 시작한 뒤로는 기존 항목을 지우거나 덮어쓰지 않는다).
  - `name`은 몇 차 시도인지 순번을 이어서 붙인다 (예: "4차 시도").
  - `설명`에는 무엇을 바꿨는지 한 줄로 적는다.
- 혼동행렬, 잔차 플롯, error_breakdown, feature_importance 등은 가장 최신 결과로 갱신한다.
- 수정 후 사용자에게 "대시보드에 N차 시도 결과를 반영했습니다" 처럼 간단히 알린다.

### (b) 명시적 요청 — 그 외 모든 기록
위 (a)에 해당하지 않는 대시보드 변경(레이아웃, 문구, 새 섹션 추가, 색상 등)은 **사용자가 명시적으로 요청했을 때만** 수정한다. 먼저 묻지 않고 임의로 대시보드 구조를 바꾸지 않는다.

## 4. 분석 방향 제안은 사용자가 먼저 물어봤을 때만

사용자가 "어떻게 하면 좋을지", "다음에 뭘 해볼지", "이 결과 어떻게 해석해야 할지" 등을 **명시적으로 물어보지 않는 이상**, 다음 분석 방향·개선 아이디어·해석·가이드를 먼저 제안하지 않는다.

- 지시받은 작업만 정확히 수행하고 결과를 보고한다.
- "다음엔 이렇게 해보는 게 어떨까요?", "이 부분이 문제일 수 있어요" 같은 조언을 스스로 덧붙이지 않는다.
- 사용자가 "네가 보기엔 어때?", "다음에 뭘 해보면 좋을까?", "왜 이런 결과가 나온 거야?"처럼 먼저 물어보면 그때는 성실하게 방향을 제안하고 설명한다.

## 5. 설명은 비개발자 눈높이로

사용자는 개발자가 아니다. 코드나 결과를 설명할 때 다음을 지킨다.

- 전문 용어(하이퍼파라미터, 오버피팅, 스케일링 등)를 쓸 때는 짧게 풀어서 같이 설명한다.
- 코드 자체를 보여주기보다 "무엇을 했고, 결과가 뭘 의미하는지" 중심으로 설명한다.
- 에러가 나면 원인을 개발 용어로만 설명하지 말고, 사용자가 다음에 뭘 하면 되는지(예: "이 파일을 다시 업로드해 주세요") 쉬운 말로 안내한다.
- 보고할 때는 숫자만 나열하지 말고 "좋아진 건지 나빠진 건지", "왜 중요한지"를 한두 문장으로 덧붙인다. 단, 이는 지시받은 작업 결과를 보고하는 맥락에서만 해당하며, 위 4번 규칙(먼저 방향을 제안하지 않는 것)과는 별개다 — 결과 해석은 보고하되, 다음 행동을 먼저 제안하지는 않는다.

## 6. 하지 말아야 할 것

- 모델을 학습시켜놓고 experiments/에 남기지 않고 노트북에서만 결과를 보여주고 끝내는 것
- 작업 지시(EDA/모델링)를 받았다고 바로 `dashboard_template.py`를 여는 것
- `runs` 리스트나 기존 지표를 덮어써서 이전 시도 기록을 잃어버리는 것
- 사용자가 결과를 확인하기도 전에 대시보드부터 먼저 고치는 것
- 사용자가 묻지 않았는데 다음 분석 방향이나 개선 아이디어를 먼저 제안하는 것
- 결과나 에러를 개발자 용어로만 설명하고 넘어가는 것
- 사용자가 기록을 요청하지 않았는데 EDA/전처리 노트북 탐색을 experiments/로 임의 승격시키는 것
